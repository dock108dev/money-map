# Personal and small-group use

Updated October 7, 2026. The current goal is a useful tool for the owner and a handful of users.

Use the existing local app or source startup. Make one useful improvement, check the affected behavior, and get ordinary-use feedback. Users can try working parts while other features are unfinished. Keep private data separate for each person; another person can use their own local installation. Shared hosting or a network service needs its own concrete use case and is not a current task.

## Checks that matter now

- The changed flow works and saves/reopens as expected.
- Existing data and credentials survive updates; back up before changing personal data or its schema.
- Calculations and external-source labels are honest, and paid requests keep their existing limits.
- Gameplay/input, playback and owned processes stop or hand back as expected on the path being used.

Choose focused checks for the actual change. Build only when needed to run updated code or assets. A documentation-only change needs a documentation/link check. Broader regression runs are appropriate when a change touches shared behavior or a reproduced fault justifies them.

Public-release roadmaps, notarization, installer production, platform/device matrices, repeated candidate manifests, mandatory full-suite handoffs, formal acceptance campaigns and hosted-readiness work are outside the current worklist. Existing scripts and CI remain available; their presence does not make them prerequisites to personal use. Preserve existing platform permissions, app identity, security controls and account/data-access rules.

## Documentation ownership

Current next-step trackers and concise product/operation guides own work order. Dated reports, old assignments, release records and retained evidence describe their original runs. They do not dispatch new work or block early user feedback. Update current docs for changed behavior without regenerating historical evidence.
